# Minimal Bugfix

症状を直し、原因と検証結果を追跡可能にする。作業の目的は、要求された不具合の修正であり、無関係な改善や設計変更を広げることではない。

## Workflow

1. **契約と範囲を確認する**。ユーザーの期待動作、対象コード、互換性・安全性の制約、プロジェクトの docs・CI・test に書かれた契約を調べる。プロジェクト固有の契約が見つからない場合は、その事実と参照した根拠を記録し、重要な不明点だけ質問する。
2. **baseline を記録する**。秘密値を含まない最小の再現データ・証拠、再現手順、環境、期待結果、実際の結果、関連テストを記録する。再現できない場合は未解決として扱い、推測だけで修正済みにしない。既存テストの失敗は変更前からの失敗として分けて記録する。
3. **原因を絞る**。必要な診断・計測・一時的なログやテストは追加してよい。利用可能なら `diagnosing-bugs` など既存の診断 Skill を使い、欠落していても同等の再現・切り分けを行う。緊急緩和策と根治策を区別する。
4. **最小必要修正を行う**。原因を解消し、既存契約を保つ変更だけを採用する。既存実装の再利用は要求とプロジェクト契約に適合する場合に限る。新しい抽象化、依存、設定、互換層は具体的な必要性がある場合だけ追加する。
5. **回帰を検証する**。再現ケースが失敗から成功へ変わったこと、関連する既存動作が維持されたこと、追加した診断用変更を撤去または恒久化したことを確認する。テスト未実行・再現未確認・既存失敗のみの場合は成功と報告しない。
6. **独立レビューを受ける**。実装者とは別のレビュー工程で、原因との対応、変更範囲、互換性、安全性、回帰証拠を確認する。利用可能なら適切な review Skill を使い、なければ同等の別工程を行う。Issue 起票、PR 作成、配備は依頼されていない限り行わない。

## Completion

次の全てを満たしたときだけ完了とする。

- baseline と原因の根拠が記録されている。
- 再現ケースが修正後に通り、関連検証の結果と変更前からの失敗が区別されている。
- 変更が不具合の原因に必要な範囲へ収まり、診断用の一時変更が残っていない。
- 独立レビューで未解決の重大な指摘がなく、未検査や再現不能を成功扱いしていない。
